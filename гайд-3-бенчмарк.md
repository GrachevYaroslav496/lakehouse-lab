# Гайд 3. Бенчмарк форматов и кодеков: Parquet vs ORC

Продолжение гайда 1. Работаем поверх уже поднятого стека **MinIO → Lakekeeper → Trino**. Только теперь мы ничего не «строим», а **меряем**: пишем один и тот же датасет в разные форматы и кодеки, а потом сравниваем размер, время записи и скорость запросов.

> ⚠️ **Важно перед стартом (обновление 2026).**
>
> **1. Образы MinIO.** Официальные образы больше не раздаются бесплатно: `minio/minio` удалён с Docker Hub, `quay.io/minio/minio` и `quay.io/minio/mc` отвечают `401`, а AIStor требует лицензию. Используй свободный форк **Silo** — команды, порты и переменные окружения те же, меняется только имя образа:
> - сервер: `pgsty/silo:latest` (вместо `minio/minio` / `quay.io/minio/minio`);
> - клиент `mc`: `pgsty/mc:latest` (вместо `minio/mc` / `quay.io/minio/mc`).
>
> **2. Каталоги `tpch` и `bench` не появляются сами.** `tpch` — встроенный коннектор Trino, но виден только после того, как ты создашь `catalog/tpch.properties` и перезапустишь Trino. `bench` — Iceberg-каталог поверх warehouse `bench` (бакет `bench` в MinIO), для него нужен `catalog/bench.properties` + перезапуск. Оба шага — в §2–3. Пока они не сделаны, `SHOW SCHEMAS FROM tpch` и любой SQL к `bench` падают с `Catalog '…' not found`.

## 0. Что мы делаем и зачем

В предыдущих гайдах данные всегда ложились в хранилище как **Parquet** — это было «само собой». Здесь мы разберёмся, что этот выбор стоит денег, и научимся его принимать осознанно.

**Что меряем:**

| Метрика | Что показывает | Во что переводится |
|---|---|---|
| **Размер** на диске | сколько места заняли файлы данных | стоимость хранения (платим за каждый ГБ в месяц) |
| **Время записи** | сколько секунд писались данные | стоимость/время загрузки (ETL) |
| **Скорость агрегаций** | сколько секунд считается `GROUP BY` | стоимость аналитики (платим за время работы кластера) |

Итог — практическое понимание компромисса **«размер ↔ скорость ↔ стоимость»**: сжать сильнее = дешевле хранить, но дольше писать и читать; не сжимать = быстрее, но дороже.

### Данные

Берём стандартный бенчмарк **TPC-H** — это «эталонная» база данных оптовой торговли, на которой принято сравнивать движки. Нас интересует таблица **`lineitem`** (строки заказов): 16 колонок — числа, суммы, проценты, даты, короткие строки. Идеальный микс типов для сравнения кодеков.

Данные генерирует **встроенный коннектор TPC-H** в Trino — он ничего не хранит, а «придумывает» строки на лету по детерминированному алгоритму. Чтобы получить реальные файлы, мы записываем результат в Iceberg-таблицу командой `CREATE TABLE ... AS SELECT`.

### «Ручка» объёма — scale factor

Объём задаётся одной цифрой в имени схемы `tpch.sf<N>`. Чем больше `N`, тем больше строк и гигабайт:

| Схема | Строк в `lineitem` | Сырой размер `lineitem` | Для чего |
|---|---|---|---|
| `tpch.tiny` | 60 тыс. | ~1 МБ | проверить, что SQL вообще работает |
| `tpch.sf1` | 6 млн | ~0.7 ГБ | слабый ноутбук / разминка |
| `tpch.sf10` | 60 млн | ~7 ГБ | **дефолт этой лабораторной** |
| `tpch.sf100` | 600 млн | ~70 ГБ | полный масштаб «десятки гигабайт» из задания |

> 💡 **«50 ГБ» из задания = `sf100`.** Сырой `lineitem` на sf100 весит ~70 ГБ, после сжатия — это те самые «десятки гигабайт». Но 8 таблиц (2 формата × 4 кодека) на sf100 — это сотни ГБ на диске и десятки минут на каждую запись. Поэтому дефолт — **`sf10`** (~7 ГБ сырых, всё считается за минуты), а на `sf100` переходим, когда всё отлажено и есть свободное место на диске + 8–16 ГБ RAM. Меняется одна цифра в SQL — и всё, остальной гайд не трогаем.

> 💡 **`SHOW SCHEMAS FROM tpch` покажет не все факторы** (в списке есть `sf1`, `sf100`, `sf300`, `sf1000`…, но нет `sf10`/`sf50`). Это не ошибка — коннектор принимает любой `sfN`: просто подставляй нужное `N` в `tpch.sfN`.

### Форматы и кодеки — коротко

**Форматы** (оба колоночные — хранят данные по колонкам, а не по строкам):

- **Parquet** — де-факто стандарт в дата-инжиниринге, лучшая экосистема.
- **ORC** — «родной» формат Hive, вписан в его экосистему; на вложенных типах бывает компактнее, на плоских таблицах — обычно сопоставим с Parquet.

**Кодеки** (что сжимает байты внутри колонок):

| Кодек | Сжатие | Скорость | CPU | Типичное применение |
|---|---|---|---|---|
| `NONE` | нет (эталон) | максимум | нет | «сырой» бейзлайн |
| `SNAPPY` | слабое | быстро | мало | дефолт Parquet |
| `GZIP` | сильное | медленно | много | архивные/редкочитаемые данные |
| `ZSTD` | сильное, как GZIP | быстро, как SNAPPY | средне | современный компромисс |

> В ORC кодек `GZIP` называется `ZLIB` — но в Trino значение свойства одно и то же (`GZIP`), коннектор сам подставит нужное имя для каждого формата.

## 2. Шаг 1 — бакет `bench` и warehouse `bench`

Данные бенчмарка держим отдельно — в своём бакете и своём warehouse.

**2.1. Бакет `bench` в MinIO.** Открой http://localhost:9001 → логин `minioadmin` / `minioadmin`. Слева **Buckets → Create Bucket → имя `bench` → Create Bucket**.

Альтернатива через `mc`:

```bash
docker run --rm --entrypoint /bin/sh --add-host host.docker.internal:host-gateway \
  pgsty/mc:latest -c "mc alias set m http://host.docker.internal:9000 minioadmin minioadmin && mc mb --ignore-existing m/bench"
```

**2.2. Warehouse `bench` в Lakekeeper** (регистрируем через API):

```bash
curl -X POST http://localhost:8181/management/v1/warehouse \
  -H "Content-Type: application/json" \
  -d '{
    "warehouse-name": "bench",
    "project-id": "00000000-0000-0000-0000-000000000000",
    "storage-profile": {
      "type": "s3",
      "bucket": "bench",
      "key-prefix": "",
      "endpoint": "http://host.docker.internal:9000",
      "region": "us-east-1",
      "path-style-access": true,
      "flavor": "s3-compat",
      "sts-enabled": false
    },
    "storage-credential": {
      "type": "s3",
      "credential-type": "access-key",
      "access-key-id": "minioadmin",
      "secret-access-key": "minioadmin"
    }
  }'
```

> Ожидаемый ответ — `201 Created` со `"status":"active"`. Если `Storage profile overlaps with existing warehouse bench` — warehouse уже существует, пропускай.

## 3. Шаг 2 — каталоги `bench` и `tpch` в Trino

Trino узнаёт о warehouse и коннекторах из `.properties`-файлов в папке `catalog/`. Эта папка примонтирована внутрь Trino ещё в гайде 1 — достаточно положить в неё файл и перезапустить Trino.

Ниже всё копируется в терминал целиком, блок за блоком. Не нужно ничего печатать руками.

**3.1. Зайди в рабочую папку и убедись, что папка `catalog/` есть:**

```bash
cd ~/lakehouse
mkdir -p catalog
```

> `cd ~/lakehouse` — рабочая папка из гайда 1 (если делал её в другом месте — подставь свой путь). `mkdir -p` создаёт папку `catalog`, если её ещё нет, и молча пропускает, если уже есть.

**3.2. Создай `catalog/bench.properties`** — скопируй блок целиком и вставь в терминал, он сам создаст файл:

```bash
cat > catalog/bench.properties << 'EOF'
connector.name=iceberg
iceberg.catalog.type=rest
iceberg.rest-catalog.uri=http://host.docker.internal:8181/catalog
iceberg.rest-catalog.warehouse=bench
iceberg.rest-catalog.nested-namespace-enabled=true
iceberg.unique-table-location=true
fs.native-s3.enabled=true
s3.endpoint=http://host.docker.internal:9000
s3.path-style-access=true
s3.region=us-east-1
s3.aws-access-key=minioadmin
s3.aws-secret-key=minioadmin
EOF
```

**3.3. Создай `catalog/tpch.properties`** (генератор данных — одна строка):

```bash
cat > catalog/tpch.properties << 'EOF'
connector.name=tpch
EOF
```

> 💡 **Проверь, что файлы легли куда надо:** `ls -l catalog/` — должны быть `bench.properties` и `tpch.properties` (плюс `lakekeeper.properties` из гайда 1).
>
> 🖊️ **Не нравится `cat`?** Можно и через редактор: `nano catalog/bench.properties` → вставь содержимое → `Ctrl+O` → `Enter` → `Ctrl+X`. Аналогично `nano catalog/tpch.properties` со строкой `connector.name=tpch`.

**3.4. Перезапусти Trino** (файлы читаются только при старте):

```bash
docker restart trino
```

Подожди ~30 секунд и проверь, что каталоги появились:

```bash
docker exec trino trino --execute "SHOW CATALOGS"
```

Должны быть: `bench`, `tpch` (плюс служебный `system` и `lakekeeper` из гайда 1).

## 4. Шаг 3 — 8 таблиц: 2 формата × 4 кодека

Создаём схему и 8 таблиц — по одной на каждую комбинацию «формат × кодек». Имя таблицы кодирует оба параметра: `lineitem_<формат>_<кодек>`.

**4.1. Схема:**

```sql
CREATE SCHEMA bench.lakehouse;
```

**4.2. Первая таблица (шаблон).** Выполни **две** строки подряд и засеки время:

```sql
SET SESSION bench.compression_codec = 'ZSTD';

CREATE TABLE bench.lakehouse.lineitem_parquet_zstd
WITH (format = 'PARQUET')
AS SELECT * FROM tpch.sf10.lineitem;
```

Два параметра, которыми мы управляем:

- `format` — **свойство таблицы** (задаётся в `WITH`): `'PARQUET'` или `'ORC'`.
- `compression_codec` — **свойство сессии** (задаётся `SET SESSION` **до** создания таблицы): `'NONE'`, `'SNAPPY'`, `'GZIP'` или `'ZSTD'`. Применяется к таблице, которую создаёшь в этой же сессии.

> ⚠️ **Почему кодек не в `WITH`?** В коннекторе Iceberg у Trino `compression_codec` — это свойство *сессии*, а не *таблицы*: попытка `WITH (compression_codec = ...)` упадёт с `table property 'compression_codec' does not exist`. Поэтому кодек задаём отдельной командой `SET SESSION` перед `CREATE TABLE`. В DBeaver выполняй обе строки вместе (они идут в одной сессии).

Всё остальное (`SELECT * FROM tpch.sf10.lineitem`) не меняется — данные одни и те же, отличается только то, как они лягут на диск.

> ⚠️ **Что произошло:** Trino сгенерировал ~60 млн строк `lineitem`, записал их файлами нужного формата/кодека в бакет `bench` и зарегистрировал таблицу в Lakekeeper. Данные из `tpch` на самом деле нигде не «хранились» — мы их только что материализовали в Iceberg.

**4.3. Остальные 7 таблиц.** Те же две строки: сначала `SET SESSION bench.compression_codec = '<кодек>'`, затем `CREATE TABLE ... WITH (format = '<формат>')`. Меняются только кодек, формат и имя таблицы:

| # | Таблица | `format` | `compression_codec` |
|---|---|---|---|
| 1 | `lineitem_parquet_zstd` | PARQUET | ZSTD |
| 2 | `lineitem_parquet_none` | PARQUET | NONE |
| 3 | `lineitem_parquet_snappy` | PARQUET | SNAPPY |
| 4 | `lineitem_parquet_gzip` | PARQUET | GZIP |
| 5 | `lineitem_orc_zstd` | ORC | ZSTD |
| 6 | `lineitem_orc_none` | ORC | NONE |
| 7 | `lineitem_orc_snappy` | ORC | SNAPPY |
| 8 | `lineitem_orc_gzip` | ORC | GZIP |

> 💡 **Мало места на диске?** Начни с 4 таблиц вместо 8 (например `parquet_zstd`, `parquet_none`, `orc_zstd`, `orc_gzip`) — этого хватит, чтобы увидеть главные закономерности. Каждая таблица на `sf10` занимает от ~2 до ~7 ГБ.

> ⚠️ **Кодек `NONE` и совместимость.** Trino пишет в метаданные литеральное `NONE`. Внутри этой лабораторной всё читается нормально (Trino читает собственные таблицы), но если ту же таблицу позже читать Spark'ом, «без сжатия» для Parquet/ORC там ожидается как `uncompressed`/`none` — могут быть сюрпризы. Это не мешает бенчмарку, просто держи в голове.

## 5. Шаг 4 — замеряем размер

Размер таблицы смотрим не в MinIO (там файлы раскиданы по uuid-папкам), а через **системную таблицу Iceberg `$files`** — она перечисляет каждый файл данных с его размером в байтах.

Для одной таблицы:

```sql
SELECT count(*)                AS files,
       sum(file_size_in_bytes) AS bytes
FROM bench.lakehouse."lineitem_parquet_zstd$files";
```

- `files` — сколько файлов данных породила запись;
- `bytes` — суммарный размер данных (подели на 1024³, чтобы получить ГБ).

> ⚠️ **Кавычки обязательны:** имя системной таблицы содержит `$`, поэтому пишем её в двойных кавычках целиком: `"lineitem_parquet_zstd$files"`. Без кавычек Trino не поймёт имя.

Повтори запрос для каждой из 8 таблиц и занеси `bytes` в таблицу результатов (§10).

Самый быстрый способ собрать всё разом — один запрос по всем таблицам:

```sql
SELECT 'parquet_zstd'  AS t, sum(file_size_in_bytes) AS bytes FROM bench.lakehouse."lineitem_parquet_zstd$files"
UNION ALL SELECT 'parquet_none',  sum(file_size_in_bytes) FROM bench.lakehouse."lineitem_parquet_none$files"
UNION ALL SELECT 'parquet_snappy',sum(file_size_in_bytes) FROM bench.lakehouse."lineitem_parquet_snappy$files"
UNION ALL SELECT 'parquet_gzip',  sum(file_size_in_bytes) FROM bench.lakehouse."lineitem_parquet_gzip$files"
UNION ALL SELECT 'orc_zstd',      sum(file_size_in_bytes) FROM bench.lakehouse."lineitem_orc_zstd$files"
UNION ALL SELECT 'orc_none',      sum(file_size_in_bytes) FROM bench.lakehouse."lineitem_orc_none$files"
UNION ALL SELECT 'orc_snappy',    sum(file_size_in_bytes) FROM bench.lakehouse."lineitem_orc_snappy$files"
UNION ALL SELECT 'orc_gzip',      sum(file_size_in_bytes) FROM bench.lakehouse."lineitem_orc_gzip$files";
```

**Загляни и в свойства самой таблицы** — формат, кодек, партиции и статистику. Это те же характеристики, что мы меряем, но увиденные «изнутри» Iceberg-метаданных (именно их читают движки, когда строят план запроса).

**Формат и кодек.** Кодек записался в файлы на шаге §4 через `SET SESSION compression_codec`, поэтому в `SHOW CREATE TABLE` его нет — там виден только `format = 'PARQUET'`. Сам формат и кодек лежат в свойствах таблицы (`$properties`):

```sql
SELECT key, value
FROM bench.lakehouse."lineitem_parquet_zstd$properties"
WHERE key LIKE 'write.%.compression-codec'
   OR key = 'write.format.default';
```

Для `lineitem_parquet_zstd` получишь `write.format.default = PARQUET` и `write.parquet.compression-codec = zstd`. Для ORC-таблиц вместо `write.parquet.*` будет `write.orc.*` (а `GZIP` там запишется как `zlib` — см. примечание в §0).

> ⚠️ **Почему в `SHOW CREATE TABLE` кодек не видно.** `compression_codec` — это свойство *сессии* (шаг §4), а не таблицы: Trino применяет его в момент записи и не кладёт в DDL. Поэтому `SHOW CREATE TABLE` у `lineitem_parquet_zstd` и `lineitem_parquet_gzip` выглядит **одинаково** (`format = 'PARQUET'` и всё). Разница видна только через `$properties` (`write.parquet.compression-codec`) и по размеру файлов. Это нормально — не значит, что кодек «не сработал».

**Партиции.** Таблицы создавались без `PARTITIONED BY`, поэтому партиция ровно одна — вся таблица. Системная таблица `$partitions` это подтверждает (ровно одна строка):

```sql
SELECT record_count, file_count, total_size
FROM bench.lakehouse."lineitem_parquet_zstd$partitions";
```

- `record_count` — строк в партиции (≈ 60 млн на `sf10`);
- `file_count` — число файлов данных (на `sf10` их ~12 — Trino пишет кусками по ~2 ГБ);
- `total_size` — суммарный размер в байтах (сходится с `bytes` из `$files`).

**Статистика.** `SHOW STATS FOR` показывает собранные Trino статистики по каждой колонке:

```sql
SHOW STATS FOR bench.lakehouse.lineitem_parquet_zstd;
```

Что смотреть:

- `distinct_values_count` — уникальных значений (NDV): у `returnflag` = 3, у `linestatus` = 2, у `orderkey` ≈ 60 млн;
- `nulls_fraction` — доля NULL (везде `0.0` — в tpch пустых нет);
- `low_value` / `high_value` — min/max колонки (например `shipdate` от `1992-01-02` до `1998-12-01`);
- последняя строка с пустым `column_name` — это итог: `row_count` = всего строк в таблице.

> 💡 Статистика собирается Trino **автоматически при записи** (`CREATE TABLE ... AS SELECT`), отдельный `ANALYZE` не нужен. Зачем она движку и как проверить её работу через `EXPLAIN` — в §11.2.

## 6. Шаг 5 — замеряем время записи

Время записи меряем утилитой `time` вокруг CLI-запроса Trino (он живёт внутри контейнера `trino`). Это точнее, чем секундомер, и не зависит от UI.

Для **каждой** таблицы выполняй команду из §4.2, обёрнутую в `time`:

```bash
time docker exec trino trino --execute \
  "SET SESSION bench.compression_codec = 'GZIP';
   CREATE TABLE bench.lakehouse.lineitem_parquet_gzip
   WITH (format = 'PARQUET')
   AS SELECT * FROM tpch.sf10.lineitem;"
```

В выводе интересует строка `real` (стены времени в секундах), например `real 0m58.412s` — это и есть время записи.

> 💡 **Почему через `docker exec`?** Утилита `trino` уже установлена внутри образа. `docker exec trino trino --execute "…"` подключается к Trino изнутри контейнера и выполняет SQL, а `time` (встроенная команда bash) засекает общее время. В DBeaver тоже можно — время показывается внизу окна результата, но через `time` цифры аккуратнее и их удобно записывать.

> ⚠️ **Ожидания:** чем сильнее кодек, тем дольше запись. `NONE` — быстрее всех (нечего жать), `GZIP` — медленнее всех (CPU молотит), `ZSTD`/`SNAPPY` — посередине. Если порядок другой — что-то с замером (см. §9 про кэш/прогрев).

## 7. Шаг 6 — замеряем скорость агрегаций

Берём классическую тяжёлую агрегацию TPC-H Q1 (полный проход по таблице + свёртка по двум колонкам) и гоняем её на каждой таблице.

Запрос (замени имя таблицы на нужную):

```sql
SELECT returnflag, linestatus,
       count(*)                            AS cnt,
       sum(quantity)                       AS sum_qty,
       sum(extendedprice)                  AS sum_price,
       sum(discount)                       AS sum_disc,
       sum(extendedprice * (1 - discount)) AS sum_charge
FROM bench.lakehouse.lineitem_parquet_zstd
GROUP BY returnflag, linestatus;
```

Это идеальный тест для кодеков: читается и суммируется практически вся таблица, так что разница между форматами/кодеками видна напрямую.

**Замер времени** — тем же `time`:

```bash
time docker exec trino trino --execute \
  "SELECT returnflag, linestatus, count(*), sum(quantity), sum(extendedprice),
          sum(discount), sum(extendedprice * (1 - discount))
   FROM bench.lakehouse.lineitem_parquet_zstd
   GROUP BY returnflag, linestatus;"
```

Повтори для всех 8 таблиц. **Каждую агрегацию прогоняй дважды** и записывай оба времени (зачем — см. §9).

> 💡 **Хочешь заглянуть «внутрь» запроса?** Вместо `time` выполни в DBeaver:
>
> ```sql
> EXPLAIN ANALYZE
> SELECT ... FROM bench.lakehouse.lineitem_parquet_zstd GROUP BY returnflag, linestatus;
> ```
>
> `EXPLAIN ANALYZE` реально выполняет запрос и показывает по каждому шагу плана его стоимость по фактическому времени (wall time) — видно, где движок провёл больше всего времени.

## 8. Шаг 7 — объём метаданных

Iceberg хранит данные и **метаданные отдельно**: помимо файлов `data/*.parquet|orc`, у каждой таблицы есть манифесты и снапшоты. Посмотрим, сколько это весит и от чего зависит.

**Манифесты текущего снапшота** (файлы-списки данных):

```sql
SELECT count(*)       AS manifests,
       sum(length)    AS manifest_bytes
FROM bench.lakehouse."lineitem_parquet_zstd$manifests";
```

**Снапшоты** (история версий таблицы):

```sql
SELECT committed_at, snapshot_id, operation
FROM bench.lakehouse."lineitem_parquet_zstd$snapshots";
```

Сравни `manifest_bytes` с размером данных из §5. Ты увидишь главное: **метаданные — это килобайты на фоне гигабайт данных.** Накладные расходы Iceberg ничтожны для больших таблиц.

**Почему тогда про метаданные вообще говорят?** Потому что их объём растёт не от размера данных, а от **числа файлов**: каждый файл данных — это строка в манифесте. Одна таблица одним большим файлом = крошечный манифест; та же таблица миллионом мелких файлов = манифесты на десятки МБ и медленное планирование каждого запроса. В §5 мы записывали число файлов (`files`) — посмотри, сколько их вышло у каждой таблицы и коррелирует ли это с временем агрегаций из §7.

> 💡 **Почему файлов больше одного?** Trino пишет данные «кусками» целевого размера (по умолчанию до ~2 ГБ на файл), поэтому большая таблица ложится в несколько файлов — это норм. Проблема «мелких файлов» (small files) — это когда файлов тысячи из-за частых мелких вставок, но в нашем `CREATE TABLE ... AS SELECT` это не так.

## 9. Шаг 8 — кэширование

Прогони одну и ту же агрегацию дважды подряд и сравни время. Почти наверняка второй прогон заметно быстрее первого. Это и есть кэш.

Два уровня кэша, которые здесь срабатывают:

1. **Кэш страниц ОС (page cache).** Когда Trino в первый раз читает файл из MinIO, операционная система держит прочитанные блоки в свободной RAM. Второй запрос читает те же блоки уже из памяти, а не с диска. На `sf10` данные (~7 ГБ) частично не влезают в RAM — эффект виден, но не всегда «в разы»; на `sf1` вся таблица влезает в RAM, но помни: данные, которые только что записали, уже лежат в кэше, поэтому «холодный» замер без перезапуска MinIO получить не удастся.
2. **Кэш метаданных Trino.** Iceberg-метаданные (манифесты, снапшоты) Trino кэширует после первого обращения — последующие запросы не ходят за ними в Lakekeeper/MinIO.

**Зачем это для бенчмарка.** «Честное» время — это **холодный** (первый) прогон: именно он показывает реальную стоимость чтения с диска. Тёплый прогон показывает «лучший случай» с прогретым кэшем. Поэтому в таблицу результатов (§10) записывай **оба** времени: `cold` и `warm`. Если в учебной задаче кто-то меряет только один прогон — его цифры можно не сравнивать с твоими: у него мог быть прогретый кэш.

> 💡 **Сбросить кэш для честного замера.** Кэш двух видов, и сбрасывается по-разному:
>
> - **Данные (page cache ОС)** — перезапусти MinIO: `docker restart lakehouse-minio`.
> - **Внутренний кэш Trino** (метаданные Iceberg: таблицы, манифесты, снапшоты) — перезапусти сам Trino: `docker restart trino`. Отдельной команды flush для Iceberg нет: `CALL system.flush_metadata_cache()` — это процедура Hive-коннектора, и в нашем стеке (только Iceberg) она не зарегистрирована.
>
> На практике для учебного бенчмарка достаточно: перезапусти стек (`docker restart trino lakehouse-minio`), прогнал агрегацию — это «холодный» прогон (`cold`), прогнал второй раз — «тёплый» (`warm`).

### 11.1 Параллельный запуск: 10 потоков

Официальный бенчмарк TPC-H прогоняет не один запрос, а **набор одновременных «потоков»** (streams): это ближе к реальной нагрузке, где несколько аналитиков бьют по одному хранилищу одновременно. Заодно это проверяет, как движок **делит ресурсы** между запросами.

**Идея:** один и тот же тяжёлый запрос запускаем один раз и засекаем время, потом — десятью копиями одновременно и снова засекаем. Если бы запросы не мешали друг другу, 10 штук заняли бы `10 × t`; на деле они конкурируют за CPU, поэтому выходит меньше, чем `10 × t`, но больше, чем `t`.

**1. Базовая точка — один запрос:**

```bash
time docker exec trino trino --execute \
  "SELECT sum(extendedprice) FROM bench.lakehouse.lineitem_parquet_zstd_sf1"
```

Запиши `real` (например `1.2s`).

**2. Десять потоков одновременно** (bash запускает 10 копий в фоне и ждёт все):

```bash
time bash -c '
for i in $(seq 1 10); do
  docker exec trino trino --execute \
    "SELECT sum(extendedprice) FROM bench.lakehouse.lineitem_parquet_zstd_sf1" \
    >/dev/null 2>&1 &
done
wait
'
```

`real` в конце — это **время всей пачки** из 10 запросов (например `5s`).

**Как читать цифры:**

| Метрика | Формула | У тебя |
|---|---|---|
| Пропускная способность, 1 поток | `1 / t_одиночный` | 0,230|
| Пропускная способность, 10 потоков | `10 / t_пачки` | 1,643|
| Во сколько раз замедлился каждый запрос | `t_пачки / t_одиночный` | 1,397|

Ты почти наверняка увидишь: **суммарная пропускная способность выросла** (с одного запроса в `t` секунд до нескольких в секунду), но **каждый отдельный запрос стал медленнее** — все 10 делят одни и те же ядра CPU. Это и есть конкуренция за ресурсы: у Trino ограниченное число воркер-потоков на узел.

> 💡 **Почему это важно для бенчмарка.** Одиночный запрос меряет «максимальную скорость», а параллельный — «сколько реально выдержит система под нагрузкой». В продакшене решает именно вторая цифра, поэтому в отчёт заносят обе: `single` и `throughput`.

> ⚠️ **Почему на sf1, а не sf10.** На sf10 десять одновременных полных проходов по ~7 ГБ просто забьют память/CPU ноутбука, и эффект конкуренции утонет в свопе. На sf1 (~250 МБ) он виден чисто, без артефактов.

### 11.2 Статистика: как собрать и проверить

Чтобы выбрать хороший план запроса, движку нужны **статистики таблицы**: сколько строк, сколько уникальных значений в колонке (**NDV** — number of distinct values), какая доля NULL, минимум/максимум. Без них оптимизатор «стреляет вслепую» и может выбрать плохой план (например, broadcast-join вместо hash-join на большой таблице).

**1. Посмотри, что уже собрано** — `SHOW STATS FOR`:

```sql
SHOW STATS FOR bench.lakehouse.lineitem_parquet_zstd_sf1;
```

Ключевые колонки вывода:

| Колонка | Что значит | Пример |
|---|---|---|
| `distinct_values_count` | сколько уникальных значений (NDV) | у `returnflag` — 3 |
| `nulls_fraction` | доля NULL | `0.0` = пустых нет |
| `low_value` / `high_value` | минимум / максимум | у `orderkey` — 1 и 6000000 |
| `row_count` (в строке-итоге) | всего строк в таблице | 6001215 |

> 💡 **Сюрприз: статистика уже есть.** Trino/Iceberg собирает её **автоматически при записи** (`CREATE TABLE ... AS SELECT`) — никакой `ANALYZE` для этого не нужен. Можешь проверить сам: создай таблицу и сразу выполни `SHOW STATS FOR` — NDV и min/max уже на месте.

**2. Принудительно пересчитай** — `ANALYZE`:

```sql
ANALYZE bench.lakehouse.lineitem_parquet_zstd_sf1;
```

`ANALYZE` прогоняет полный скан и переписывает статистику заново. На свежесозданной таблице цифры не изменятся (Trino посчитал их ещё при записи). `ANALYZE` нужен, когда данные **поменялись** (INSERT/MERGE/DELETE) и статистика устарела — после него планы снова точные.

**3. Убедись, что статистика реально работает** — `EXPLAIN`:

```sql
EXPLAIN SELECT count(*) FROM bench.lakehouse.lineitem_parquet_zstd_sf1
WHERE returnflag = 'A';
```

В выводе найди `Estimates: {rows: ...}`. У `returnflag` три уникальных значения, поэтому оптимизатор оценил результат фильтра как `6001215 / 3 ≈ 2000405` строк — ровно так и будет написано. Тот же фильтр по почти-уникальной колонке `orderkey` даст оценку в пару строк. Это и есть работа статистики: **не выполняя запрос, движок прикидывает, сколько строк вернётся**, и на основе этого выбирает план.

> ⚠️ **Почему это влияет на бенчмарк.** `ANALYZE` сам по себе — полный скан (на sf10 это десятки секунд), поэтому в реальном ETL его запускают отдельным шагом после загрузки, а не на каждый запрос. На наши замеры времени агрегаций статистика не влияет (там и так полный скан), но смотреть и обновлять её — обязательный навык.

### 11.3 Как собирать результаты

До сих пор мы записывали время «руками» из вывода `time`. Это работает, но не масштабируется: 8 таблиц × (запись + агрегация ×2) = десятки цифр, которые легко перепутать. Правильный способ — **вытаскивать время самих запросов из системной таблицы Trino**.

Каждый выполненный запрос Trino логирует в `system.runtime.queries` — там есть и текст запроса, и его времена:

```sql
SELECT query_id,
       state,
       queued_time_ms,
       analysis_time_ms,
       planning_time_ms,
       date_diff('millisecond', started, "end") AS exec_ms,
       query
FROM system.runtime.queries
WHERE query LIKE '%lineitem_parquet_zstd_sf1%'
  AND query NOT LIKE '%runtime.queries%'   -- отсекаем сам этот запрос
ORDER BY created DESC
LIMIT 20;
```

Что тут важно:

- `date_diff('millisecond', started, "end")` — чистое время выполнения запроса (без ожидания в очереди). **`"end"` обязательно в двойных кавычках** — `end` зарезервированное слово.
- `queued_time_ms` — сколько запрос простоял в очереди (растёт, если запустить много потоков одновременно — из §11.1).
- `analysis_time_ms` / `planning_time_ms` — сколько Trino думал над планом (обычно миллисекунды).

Прогони агрегацию из §7 на паре таблиц, затем выполни запрос выше — увидишь свои запросы с временем. Сверь `exec_ms` с тем, что показал `time`: цифры близки, но `exec_ms` — это время именно запроса, а `time` включал ещё и старт CLI.

> 💡 **Собери результаты в файл.** Чтобы не переписывать цифры, результат любого запроса можно слить в CSV:
>
> ```bash
> docker exec trino trino --output-format CSV_HEADER \
>   --execute "SELECT ..." > results.csv
> ```
>
> Для бенчмарка удобно собрать один `UNION ALL` (как в §5) и слить его в `size.csv`, а времена — в `times.csv`. Файлы потом откроешь таблицей и заполнишь итоговую таблицу §10 без ручного переписывания.

### 11.4 Trino vs Spark

Trino — не единственный движок, умеющий читать Iceberg-таблицы. **Apache Spark** — batch-движок, который работает с теми же файлами в MinIO через тот же REST-каталог Lakekeeper. Прогоним **один и тот же запрос на обоих** и сравним — это прямое продолжение задания «в Spark/Trino».

**Почему Spark умеет читать наши таблицы.** Iceberg — открытый формат: и Trino, и Spark читают одни и те же `data/*.parquet` и `metadata/*.json` в бакете `bench`. Никакого экспорта/импорта не нужно — Spark подключается к тому же Lakekeeper и видит те же таблицы.

**1. Скачай jar'ы Iceberg в локальную папку.** Из рабочей папки `~/lakehouse`:

```bash
mkdir -p spark/conf spark/jars
cd spark/jars
curl -fsSL -o iceberg-spark-runtime-3.5_2.12-1.7.1.jar \
  https://repo1.maven.org/maven2/org/apache/iceberg/iceberg-spark-runtime-3.5_2.12/1.7.1/iceberg-spark-runtime-3.5_2.12-1.7.1.jar
curl -fsSL -o iceberg-aws-bundle-1.7.1.jar \
  https://repo1.maven.org/maven2/org/apache/iceberg/iceberg-aws-bundle/1.7.1/iceberg-aws-bundle-1.7.1.jar
cd ../..
```

**2. Файл `spark/conf/spark-defaults.conf`** (Spark читает его при старте — так же, как Trino читает `catalog/*.properties`):

```properties
spark.sql.extensions                        org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions
spark.sql.catalog.bench                     org.apache.iceberg.spark.SparkCatalog
spark.sql.catalog.bench.catalog-impl        org.apache.iceberg.rest.RESTCatalog
spark.sql.catalog.bench.uri                 http://host.docker.internal:8181/catalog
spark.sql.catalog.bench.warehouse           bench
spark.sql.catalog.bench.io-impl             org.apache.iceberg.aws.s3.S3FileIO
spark.sql.catalog.bench.s3.endpoint         http://host.docker.internal:9000
spark.sql.catalog.bench.s3.path-style-access true
spark.sql.catalog.bench.s3.access-key-id    minioadmin
spark.sql.catalog.bench.s3.secret-access-key minioadmin
spark.sql.catalog.bench.s3.region           us-east-1
spark.jars                                  /opt/spark/iceberg-jars/iceberg-spark-runtime-3.5_2.12-1.7.1.jar,/opt/spark/iceberg-jars/iceberg-aws-bundle-1.7.1.jar
```

> ⚠️ **Зачем `io-impl=S3FileIO` и `s3.*`?** По умолчанию Spark-клиент Iceberg пробует читать `s3://` через Hadoop (`HadoopFileIO`), который про схему `s3` не знает — получишь `No FileSystem for scheme "s3"`. Строки `io-impl` и `s3.*` явно переключают его на S3-клиент и указывают адрес/креды MinIO.

> ⚠️ **Почему jar'ы не через `--packages`?** Так можно (`--packages org.apache.iceberg:...`), но Spark тянет их через ivy при каждом старте — медленно и капризно. Скачать один раз в папку и смонтировать — надёжнее.

**3. Запусти Spark**, смонтировав папки с конфигом и jar'ами (как у Trino). Интерактивно — флаг `-it`:

```bash
docker run -it --rm \
  --add-host host.docker.internal:host-gateway \
  -v "$(pwd)/spark/conf:/opt/spark/conf" \
  -v "$(pwd)/spark/jars:/opt/spark/iceberg-jars" \
  apache/spark:3.5.3 \
  /opt/spark/bin/spark-sql
```

> ⚠️ **Почему jar'ы монтируем в `/opt/spark/iceberg-jars`, а не в `/opt/spark/jars`?** В `/opt/spark/jars` лежат собственные jar'ы самого Spark — если смонтировать туда поверх, Spark потеряет свои библиотеки и не запустится (`ClassNotFoundException: org.apache.spark.launcher.Main`). Поэтому для наших jar'ов — отдельная папка, а в конфиге путь `/opt/spark/iceberg-jars/...`.

Через ~15–30 секунд (старт JVM + SparkContext) появится приглашение `spark-sql>`. Проверь, что Spark видит те же таблицы:

```sql
SHOW TABLES IN bench.lakehouse;
```

**4. Прогони тот же Q1, что на Trino** (в `spark-sql>`):

```sql
SELECT returnflag, linestatus,
       sum(quantity) AS sum_qty,
       sum(extendedprice) AS sum_price,
       sum(extendedprice * (1 - discount)) AS sum_disc,
       count(*) AS cnt
FROM bench.lakehouse.lineitem_parquet_zstd_sf1
WHERE shipdate <= DATE '1998-12-01'
GROUP BY returnflag, linestatus
ORDER BY returnflag, linestatus;
```

Spark вернёт **те же числа**, что и Trino (те же файлы, тот же формат) — это хорошая проверка, что оба движка читают одно и то же. Чтобы выйти из `spark-sql>`: `quit;` или `Ctrl-D`.

**5. Замерь время разовым прогоном** (не интерактивно, с `time`):

```bash
time docker run --rm \
  --add-host host.docker.internal:host-gateway \
  -v "$(pwd)/spark/conf:/opt/spark/conf" \
  -v "$(pwd)/spark/jars:/opt/spark/iceberg-jars" \
  apache/spark:3.5.3 \
  /opt/spark/bin/spark-sql -e \
  "SELECT returnflag, linestatus, sum(quantity), sum(extendedprice),
          sum(extendedprice * (1 - discount)), count(*)
   FROM bench.lakehouse.lineitem_parquet_zstd_sf1
   WHERE shipdate <= DATE '1998-12-01'
   GROUP BY returnflag, linestatus
   ORDER BY returnflag, linestatus;"
```

В выводе Spark ищи строку `Time taken: N seconds` — это время самого запроса. Сравни с Trino (§7) и заполни:

| Движок | Время одного Q1 (sf1) | Примечание |
|---|---|---|
| Trino | ~1.5 с | старт CLI почти мгновенный |
| Spark | ~5 с (запрос) + ~5 с (старт JVM) | смотри `Time taken` в выводе |

**Что из этого следует** (это и есть вывод эксперимента):

- **Trino** — интерактивный SQL-движок: быстрый старт, на малом объёме считает одиночные запросы быстрее. Заточен под ad-hoc аналитику поверх данных.
- **Spark** — batch-движок: платит «налог на старт» (JVM + SparkContext + инициализация каталога), поэтому одиночный маленький запрос ему «невыгоден». Его сила — распределённые ETL-пайплайны, масштабирование на десятки узлов и большие объёмы, где старт окупается.

> 💡 **Честность сравнения.** Сравнивай именно **время выполнения запроса** (у Spark это строка `Time taken`), а не «стены времени» `time docker run` — последняя включает ещё старт контейнера и JVM. На sf1 разрыв в пользу Trino; на по-настоящему больших данных (sf100+) и на кластере из нескольких узлов Spark этот разрыв сокращается — это тема для отдельного эксперимента.

## 13. Полный тест TPC-H (22 запроса) на Spark: конкуренция и throughput

До сих пор на Spark (§11.4) мы гоняли **один** запрос Q1 и сравнивали его с Trino. Теперь — **весь тест TPC-H целиком**: все 22 запроса на Spark, по данным масштаба `sf5`, в **10 конкурентных потоков**, с замером времени и пропускной способности.

> 📁 **Все файлы этой части лежат в папке `tpch-spark/`** (рядом с этим гайдом): `materialize_sf5.sql`, `queries/q01.sql…q22.sql`, `tpch_run.py`, `spark-defaults.conf`. Дальше по тексту «эта папка» = `tpch-spark/`.

### 13.1 Что такое полный TPC-H и зачем 10 потоков

**TPC-H** — эталонный бенчмарк баз данных: модель «оптовой торговли» из 8 таблиц (`lineitem`, `orders`, `customer`, `part`, `supplier`, `partsupp`, `nation`, `region`). Объём задаётся одной цифрой — **scale factor** (`sf5` = «в 5 раз больше базовой базы»). Масштаб `sf5` — это ~30 млн строк в `lineitem` и ~7,5 млн заказов: достаточно, чтобы разница между движками и режимами стала заметна, но ещё влезает в ноутбук.

**22 стандартных запроса** (`Q1`…`Q22`) покрывают разные аналитические паттерны — агрегации, джойны нескольких таблиц, подзапросы, `EXISTS`/`NOT EXISTS`, `IN`-фильтры. Один движок быстрее на одних запросах, другой — на других.

**Что мы делаем:**

1. **Материализуем данные из Trino в Iceberg.** У Trino есть встроенный коннектор `tpch`, который «придумывает» таблицы на лету. У Spark такого коннектора **нет** — поэтому сначала записываем 8 таблиц в настоящие Iceberg-таблицы в MinIO (в отдельную схему `bench.tpch`), а уже их читает Spark.
2. **Гоняем все 22 запроса на Spark** одним драйвером.
3. **Запускаем их в 10 потоков.** Это режим `throughput` из настоящего TPC-H: не «как быстро один запрос», а «сколько запросов в секунду система выдерживает, когда 10 пользователей бьют одновременно». Итого `10 × 22 = 220` исполнений.
4. **Меряем и сравниваем** — время каждого запроса и суммарную пропускную способность.

> **Почему не один поток, а десять.** Одиночный запрос показывает «максимальную скорость», параллельный — «сколько реально выдержит система». В продакшене важна вторая цифра: это и проверяет TPC-H throughput-тест.

### 13.2 Пререквизиты

Стек **MinIO → Lakekeeper → Trino** и каталоги `bench`/`tpch` уже должны быть подняты (§1–§3 этого гайда). Проверь:

curl -s http://localhost:8181/health    # 200
curl -s http://localhost:8080/v1/info   # Trino отвечает JSON

Для Spark понадобятся jar'ы Iceberg — те же, что и в §11.4; если ещё не скачал, шаг 13.5 это сделает.

### 13.4 Шаг 1 — материализовать `sf5` из Trino в Iceberg

Открой терминал **в папке `tpch-spark/`** и выполни:

```bash
docker exec -i trino trino < materialize_sf5.sql
```

Что произошло: Trino сгенерировал 8 таблиц `tpch.sf5`, записал их в Iceberg-таблицы в бакет `bench` (через Lakekeeper) и по пути переименовал колонки в каноничные имена `l_/o_/c_/...`. Это займёт несколько минут.

> 💡 **Скрипт можно запускать повторно.** Каждая таблица в нём начинается с `DROP TABLE IF EXISTS`, поэтому повторный запуск не упадёт с «`already exists`» — старые таблицы пересоздадутся заново.

> **Почему переименование.** У коннектора `tpch` колонки называются без префикса (`orderkey`, `extendedprice`), а в оригинальных 22 запросах TPC-H — с префиксом (`l_orderkey`, `l_extendedprice`). Чтобы запросы из `queries/` были 1-в-1 из спецификации, при материализации переименовываем.

> ⚠️ **Отличие от §4.** Там мы писали одну таблицу `lineitem` в схему `bench.lakehouse` (для сравнения кодеков). Здесь — **все 8 таблиц** TPC-H в отдельную схему `bench.tpch`, чтобы прогнать все 22 запроса (им нужны все таблицы).

**Проверка** (должно быть 8 таблиц и ~30 млн строк):

```bash

docker exec trino trino --execute "SELECT count(*) FROM bench.tpch.lineitem"
```

> **Мало RAM / слабый ноутбук?** Замени `sf5` на `sf1` во всех местах `materialize_sf5.sql` (это ~6 млн строк, считается за секунды). Остальное не меняется.

### 13.6 Шаг 3 — прогнать тест (Spark, 10 потоков)

По-прежнему из папки `tpch-spark/`:

```bash
docker run --rm \
  --add-host host.docker.internal:host-gateway \
  -v "$(pwd)/spark-defaults.conf:/opt/spark/conf/spark-defaults.conf" \
  -v "$(pwd)/log4j2.properties:/opt/spark/conf/log4j2.properties" \
  -v "$(pwd)/jars:/opt/spark/iceberg-jars" \
  -v "$(pwd):/opt/spark/tpch" \
  apache/spark:3.5.3 \
  /opt/spark/bin/spark-submit --master 'local[*]' \
    /opt/spark/tpch/tpch_run.py \
    --streams 10 \
    --queries /opt/spark/tpch/queries \
    --out /opt/spark/tpch/results.csv
```

Первый запуск скачает образ `apache/spark:3.5.3` (~1.5 ГБ) — это нормально. Дальше Spark стартует JVM (~15–30 с) и прогоняет 220 исполнений.

Что делают флаги:

- `--streams 10` — число конкурентных потоков (каждый прогоняет все 22 запроса);
- `--queries ...` — папка с `q01.sql`…`q22.sql`;
- `--out ...` — куда писать CSV (пишется в смонтированную папку, т.е. появится здесь же, в `tpch-spark/results.csv`).

> 💡 **`--streams 1` — это не «один запрос».** Потоки задают, сколько запросов выполняется *одновременно*, но каждый поток всё равно прогоняет все 22 запроса. `--streams 1` = 22 запроса подряд (по одному), `--streams 10` = 220 исполнений. Поэтому даже `--streams 1` идёт минуты — это полный тест, а не один запрос.

> ⚠️ **`spark-defaults.conf` из этой папки — расширенная версия из §11.4:** к нему добавлены `spark.driver.memory 7g` (sf5 ~30 млн строк требует больше дефолтного 1 ГБ; 7 ГБ хватает на 10 конкурентных потоков), `spark.scheduler.mode FAIR` (честное разделение CPU между потоками) и `spark.sql.crossJoin.enabled=true`. Подстрой `spark.driver.memory` под объём RAM машины.

> 🔕 **Куда делся INFO-спам.** По умолчанию Spark пишет `INFO` на каждый шаг — на 220 исполнений это тысячи строк лога. Монтируемый `log4j2.properties` поднимает порог до `WARN` (остаются только предупреждения и ошибки). Хочешь полную тишину — поставь в нём `rootLogger.level = error`.

> 👀 **Как понять, что прогон идёт, а не завис.** Драйвер печатает прогресс по каждому запросу: `[stream 0] q01: 5.82 с (ok)`. Пока эти строки появляются — всё работает, прогон просто долгий (первый «холодный» прогон после материализации самый медленный). Не жми Ctrl+C, пока строки идут.

### 13.7 Как читать результат и что сдать

После прогона в папке появится `results.csv` (`stream,query,seconds,status`), а в выводе драйвера — прогресс по каждому запросу и в конце сводка. Пример для одного потока:

```
Запросов: 22, потоков: 1
SparkSession готов (каталог bench.tpch), начинаю прогон...
[stream 0] q01: старт
[stream 0] q01: 5.82 с (ok)
[stream 0] q02: 3.14 с (ok)
...
[stream 0] q22: 18.40 с (ok)
Исполнений: 22, ok: 22, ошибок: 0
Общее время: 196.86 с, пропускная способность: 0.11 запросов/с
```

> Цифры выше — с машины автора (16 ГБ RAM, `sf5`, 1 поток). При `--streams 10` будет 220 исполнений (и 220 строк в CSV); сводка автора для 10 потоков — ~2196 с (0.10 запросов/с). На твоей машине будут свои числа — это нормально.

Ответь в отчёте на вопросы:

1. **Сколько исполнений, сколько `ok`, сколько `error`, какая пропускная способность?** Если есть `error` — какие запросы и почему (см. §13.8).
2. **Какой запрос самый медленный, какой самый быстрый?** Посчитай в CSV (среднее/медиану по каждому `query`). Почему одни запросы тяжелее других (какие таблицы джойнят, есть ли подзапросы)?
3. **Базовая точка для сравнения.** Прогони тот же драйвер с `--streams 1` (один поток) и сравни: суммарная пропускная способность при 10 потоках **выросла или упала**? Стал ли каждый отдельный запрос медленнее? Почему 10 потоков не дают ровно `10×` (подсказка: все делят одни ядра CPU и один общий heap — после точки насыщения конкуренция может даже *ухудшить* суммарный throughput).
4. **Trino vs Spark.** В §11.4 ты гонял Q1 на Trino. Сравни время Q1 на Spark из `results.csv` — где быстрее и почему (Spark платит «налог на старт» JVM).

> **Зачем всё это.** Ты научился не просто «запустить запрос», а прогнать стандартный бенчмарк в режиме нагрузки и снять пропускную способность — это то, чем меряются движки в реальных сравнениях.

| `OutOfMemoryError: Java heap space` на Spark | `spark.driver.memory` мал для 10 потоков на sf5 | подними `spark.driver.memory` в `spark-defaults.conf` |
| запросы `q20`/`q21` упали с `error` | ограничение Spark на глубокие коррелированные подзапросы | это известный предел Spark, а не ошибка данных — отметь в отчёте |
| `WARN RowBasedKeyValueBatch: Calling spill()... Will not spill but return 0` | на тяжёлом запросе Spark упёрся в лимит памяти и не смог сбросить промежуточные данные на диск | это НЕ ошибка и не влияет на результат (запрос досчитается в памяти); лёгкий сигнал, что памяти впритык |

### 13.9 Как почистить и поднять заново

После прогона на машине остаются: Spark-контейнер (удаляется сам), материализованные таблицы `bench.tpch.*` в MinIO (гигабайты) и результаты в папке. Чтобы прогнать лабу заново «с чистого листа»:

**Что НЕ трогаем:** стек MinIO/Lakekeeper/Trino (общий для всех лаб), файлы `queries/`, `tpch_run.py`, `spark-defaults.conf`, `materialize_sf5.sql`, `jars/`, каталог-генератор `tpch`.

**Шаг 1 — Spark-контейнер и образ.** Контейнер запускался с `--rm` — удаляется сам. Проверь:

```bash
docker ps -a | grep spark    # должно быть пусто
```

Если остался (запускал без `--rm`): `docker rm -f <имя-контейнера-spark>`. Образ `apache/spark:3.5.3` остаётся в кэше (нормально); освободить место — `docker rmi apache/spark:3.5.3` (тогда следующий прогон скачает заново).

**Шаг 2 — материализованные таблицы.** `materialize_sf5.sql` теперь сам дропает старые таблицы перед созданием (`DROP TABLE IF EXISTS`), поэтому для повторного прогона чистить ничего не нужно — просто выполни скрипт заново. `DROP SCHEMA` нужен, только если хочешь полностью сбросить схему или освободить место от «осиротевших» файлов (см. ниже):

```bash
docker exec trino trino --execute "DROP SCHEMA bench.tpch CASCADE"
```

Проверка, что чисто (схемы `tpch` под `bench` больше нет):

```bash
docker exec trino trino --execute "SHOW SCHEMAS IN bench"
```

> **Про файлы в MinIO.** Iceberg при `DROP TABLE` не стирает файлы данных сразу — оставляет их «осиротевшими». Новому прогону они не мешают: каждая таблица пишется в уникальную папку (`iceberg.unique-table-location=true`). Если нужно вернуть гигабайты диска — почисти бакет `bench` в консоли MinIO (http://localhost:9001 → Buckets → `bench` → удалить файлы) либо пересоздай бакет.

**Шаг 3 — результаты и логи в папке:**

```bash
cd tpch-spark
rm -f results*.csv run*.log
```

**Готово — поднимаем заново:**

1. `docker exec -i trino trino < materialize_sf5.sql` — материализовать данные (§13.4);
2. `docker run --rm ... apache/spark:3.5.3 ...` — прогнать тест (§13.6).

> Полная очистка всего стека (все контейнеры + тома + образы) — в §14.

### 13.10 Бонус (для рубрики p1 «звёздочка»)

Тот же `tpch_run.py` можно переиспользовать в практической p1: прогнать свой Gold-запрос в 10 потоков → «Параллельный запуск запроса (+1)». Сравнение Trino vs Spark на одном запросе → ещё +1.

## 14. Остановить и удалить всё

Таблицы бенчмарка живут в том же томе `minio-data` (бакет `bench`) и в той же базе Lakekeeper (`pg-data`), что и в гайде 1. Полная очистка — та же, что в гайде 1, §7:

```bash
# 1. Контейнеры
docker rm -f trino lakekeeper lakehouse-pg lakehouse-minio

# 2. Данные (в т.ч. бакет bench и все таблицы)
docker volume rm minio-data pg-data

# 3. Образы (скачаются заново при следующем запуске)
docker rmi trinodb/trino:476 \
          quay.io/lakekeeper/catalog:latest-main \
          postgres:17 \
          pgsty/mc:latest \
          pgsty/silo:latest \
          apache/spark:3.5.3
```

Файлы `catalog/bench.properties`, `catalog/tpch.properties` и папку `spark/` (jar'ы Iceberg + конфиг) просто удали из рабочей папки (или оставь — понадобятся при следующем запуске бенчмарка). Чтобы **просто приостановить** — `docker stop` без `rm`.
